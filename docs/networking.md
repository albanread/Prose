# Networking: how the machine gets an address, and what takes it away

The guest's network is `VZNATNetworkDeviceAttachment` over virtio-net. macOS's
`vmnet` framework builds the shared network, hands out addresses, and NATs the
traffic out to the world. None of that is ours, which is exactly why it is
worth writing down: when it fails, almost nothing on the Prose side is
involved, and the temptation is to go looking in the wrong place.

## The pieces, and where to read them

| what | where | readable as |
|---|---|---|
| shared subnet | `/Library/Preferences/SystemConfiguration/com.apple.vmnet.plist` | root only |
| DHCP pool, router, DNS, lease length | `/etc/bootpd.plist` | anyone |
| the leases themselves | `/var/db/dhcpd_leases` | anyone |
| the bridge | `ifconfig bridge100` | anyone |
| the guest's port on it | `ifconfig vmenet0` | anyone |

`/etc/bootpd.plist` is **regenerated by `com.apple.NetworkSharing` every time a
machine starts**, so it always describes the network that is actually running.
It is the file to read first, and the only one that needs no password:

```
net_address  192.168.64.0      net_mask  255.255.255.0
net_range    192.168.64.2 … 192.168.64.254      (253 addresses)
dhcp_router  192.168.64.1      dns  192.168.64.1
lease_min/max  3600
```

`bridge100` and `vmenet0` exist only while a machine is running; the last
machine to exit takes them down.

## The address the machine asks for

`makeMACAddress()` in `tools/hvgpu/controls.swift` takes one of **eight slots**,
`02:50:52:4f:53:00` … `:07`, each held by an `flock` on
`~/Library/Application Support/Prose/net-slot-N.lock`. Concurrent machines get
distinct slots; the lock dies with the process, so slots return on their own.
`--mac random` and `--mac <address>` override.

It used to derive the address from a hash of the disk image path, which meant
**every test image ever booted burned a permanent lease entry** — 115 of the 194
entries in `dhcpd_leases` were ours before this changed. `bootpd` keeps a
binding after it expires so a client gets the same address back, and reclaims
one only when it needs to, so those entries simply accumulate. Eight slots
bounds that at eight.

This is hygiene, not a fix for anything: an exhausted pool was never the
problem, and `bootpd` does reclaim when it runs out. The lease file shows it —
allocation ran `…192`, `…193`, `…194`, then wrapped to `…98`.

## When the guest has an address and still cannot connect

Work outwards from the guest and stop at the first failure. The whole sequence
needs one machine up with `--automation`:

```
osascript -e 'tell application "Prose" to execute "ifconfig"'
osascript -e 'tell application "Prose" to execute "ping -c 3 192.168.64.1"'
osascript -e 'tell application "Prose" to execute "ping -c 3 1.1.1.1"'
osascript -e 'tell application "Prose" to execute "curl -s -m 10 -o /dev/null -w %{http_code} http://example.com"'
```

| what it says | what it means |
|---|---|
| `inet addr: --`, `link configuring` | DHCP is not answering — read `/etc/bootpd.plist` and check `bridge100` is up |
| address, but gateway does not ping | the bridge or vmenet0 is wrong; almost never seen |
| gateway pings, `1.1.1.1` does not | **NAT or the host's own path out.** Not a Prose fault |
| `1.1.1.1` pings, `curl` hangs | DNS — `/boot/system/settings/network/resolv.conf` should say `nameserver 192.168.64.1` |

The guest keeps resolver settings in two places: DHCP writes
`/boot/system/settings/network/resolv.conf`, and `/etc` is a symlink to
`/boot/system/settings/etc`, so `/etc/resolv.conf` is a second, separate file.
A fresh boot may have one and not the other, so finding one missing means
nothing.

## A VPN on the host takes the guest off the internet

Measured 2026-09-23 with NordVPN. With the VPN connected:

| from the guest | |
|---|---|
| `ping 192.168.64.1` | 0.3 ms |
| `ping 192.168.1.254` (the LAN router) | 3.5 ms |
| `curl http://192.168.1.254` | HTTP 302 |
| `ping 1.1.1.1` | 100% loss |
| `curl http://example.com` | timeout |

NAT, TCP and DNS are all working — the split is **on-LAN succeeds, off-LAN
fails**, and off-LAN is what the tunnel takes. Disconnecting the VPN turned the
last two rows into 0.0% loss and HTTP 200 with nothing else changed. If the
guest has an address, reaches the gateway, reaches the LAN, and nothing else,
look at the host's VPN before looking anywhere near Prose.

**It takes DHCP with it.** A machine started while the VPN is connected gets no
address at all — `inet addr: --`, `link configuring` — and a machine that
already holds one keeps it. Three observations agree: VPN up and a fresh
hardware address got nothing; VPN down and the same address got `.196` at once;
VPN up again on the next boot and it got nothing. This is what made the pool
look exhausted, and it is why the guest could not even reach the proxy until it
was given an address by hand.

So the whole cure while a VPN is connected is **a static address and the
proxy**: Machine ▸ Network ▸ Assign a Static Address, which is verified to work
(`ifconfig <iface> <addr> <mask>`, `route add <iface> default gw <gw>`, and a
`nameserver` line in `/etc/resolv.conf`), then the proxy below for the way out.

### One test that looks useful and is not

```
ping -S 192.168.64.1 1.1.1.1      # from the Mac, sourced from the bridge
```

This fails whether or not a VPN is running, and proves nothing. vmnet NATs
*forwarded* traffic; a packet the host generates itself with a bridge source
address is not NAT'd, so the reply has nowhere to come back to. It was read as
evidence during this investigation and it was not evidence.

## Getting out while the VPN is up

`tools/guestproxy/guestproxy.py` binds an HTTP/CONNECT proxy to the bridge
address. Its outbound sockets are ordinary host sockets, so they take the Mac's
route — tunnel included — and the guest only ever talks to `192.168.64.1`.

NetSurf supports a proxy in full (`http_proxy`, `http_proxy_host`,
`http_proxy_port`, `http_proxy_auth`, `…_user`, `…_pass`, `http_proxy_noproxy`
in `/boot/home/config/settings/NetSurf/Choices`) because it is libcurl
underneath. Measured with NordVPN connected: direct `curl` gave `000` and
NetSurf rendered `https://example.com/` through the proxy in 0.0 s.

Haiku's own stack does not. `BUrlContext`/`BHttpRequest` have no proxy support,
Network preferences has no proxy UI, and `BProxySecureSocket` — which looks like
the exception — cannot connect as written, because its `sscanf` check demands 2
assignments from a format with one. So **`pkgman` and HaikuDepot cannot use a
proxy**; package work needs the VPN down. `tools/guestproxy/README.md` has the
detail.

## Changing the subnet

`com.apple.vmnet.plist` takes `Shared_Net_Address` and `Shared_Net_Mask`.
Setting them to `10.0.0.1` / `255.255.0.0` widens the pool from 253 addresses
to about 65,500:

```
sudo plutil -replace Shared_Net_Address -string 10.0.0.1 /Library/Preferences/SystemConfiguration/com.apple.vmnet.plist
sudo plutil -replace Shared_Net_Mask -string 255.255.0.0 /Library/Preferences/SystemConfiguration/com.apple.vmnet.plist
```

The keys are accepted and persist, but **vmnet does not read them until the Mac
reboots** — a machine started straight afterwards still came up on
`192.168.64.1/24` with a matching regenerated `bootpd.plist`. Check any 10.x
choice against `netstat -rn -f inet` first; this Mac already routes `10.10/16`
on `bridge0` and a VPN brings up `10.5/16`.
