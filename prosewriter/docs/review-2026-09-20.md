# ProseWriter — code review, 2026-09-20

For the agent developing `prosewriter/`. Every line reference is to the tree as
of commit `61c0b24`. I read all 8,101 lines of `app/src`, built with
`-Wall -Wextra` (46 warnings; the Makefile uses `-Wall` only), and checked each
claim below against the Haiku headers in `app/sysroot`.

**The verdict first, honestly.** This is not bad code. It is readable, the
model is sound (runs, contiguous line ownership, rows-as-paragraphs for tables),
the comments say why, and the engine work — incremental relayout, cell caret
geometry — is real engineering done fast. What it has is the debt of eight
sprints in two days: bugs a word processor cannot carry (it cannot open its own
files; it cannot type "café"; it can lose the user's document on save), a cache
that is wrong in three ways, one file holding nine classes, and a test suite
whose headline number includes a test that cannot fail and a benchmark run on a
document with 130 bytes of text. All of it is fixable, and the order below is
the order to fix it in.

---

## Part 1 — Bugs that lose work or block the user. Fix these first, in this order.

### 1. Open is broken for `.prose` and plain text. Only RTF opens.

`PWApp.cpp:1920`, `1929`, `1447`, `1512–1518`.

`BString::IFindLast()` returns `int32` — the offset, or `B_ERROR` (−1) when not
found (`support/String.h:242`, `Errors.h:52`). The code compares it to `NULL`:

```cpp
if (lower.IFindLast(".rtf") != NULL) {       // "not found" is -1, and -1 != 0
```

So a file named `report.prose` takes the RTF branch, `PW_LoadRTF` fails on the
first byte (a flattened BMessage does not start with `{`), and the user sees
"could not open that file". The compiler says so: nine `NULL used in arithmetic`
warnings, all on these lines. Commit `61c0b24` fixed the panel's completion
message; it did not fix this, so Open has never worked from the UI for the
native format. Nor has drag-and-drop typing: `isImage` at `1512` is true for
*every* dropped file (it works by accident, because `GetBitmap` fails and it
falls through). And the export at `1447` never appends `.rtf`.

**Fix:** `>= 0` in all nine places; better, one `HasSuffix(const BString&, const char*)`
helper using `IEndsWith()`, which exists and returns `bool`. Add
`-Wpointer-arith` to `CXXFLAGS` so this class of bug fails the build. Then
write the test that is missing: open a `.prose` file through `OpenFile()`, not
through `LoadFromMessage()`.

### 2. Any non-ASCII character typed is silently dropped.

`PWPageView.cpp:482–491`.

```cpp
if (numBytes == 1 && (bytes[0] & 0x80) == 0 && bytes[0] >= 32 ...)
    HandlePrintableChar(bytes, numBytes);
```

A multi-byte UTF-8 character arrives with `numBytes > 1`, fails this test, goes
to `HandleNavigationKey`, hits `default:` and is discarded. é, ü, £, €, —, and
every character of every non-English language. The document model handles
UTF-8 correctly throughout; the input path throws it away before it gets there.
There is also no `B_INPUT_METHOD_EVENT` handling, so no input method works at
all.

**Fix:** route to `HandlePrintableChar` when `numBytes > 1`, or when
`numBytes == 1 && bytes[0] >= 32` and no command/control modifier. Handle
`B_INPUT_METHOD_EVENT` (`B_INPUT_METHOD_CHANGED` with `be:string` and
`be:confirmed`) in `MessageReceived` — BTextView's implementation is the
reference. Test: feed `KeyDown("\xC3\xA9", 2)` and check the document contains
"é". Also `PWDocument.cpp:340`: undo coalescing tests `strlen(text) == 1`, so
once this works, every "é" becomes its own undo step; coalesce on "one
character" instead.

### 3. Save is not atomic, and a failed save is silent.

`PWDocument.cpp:936–955`, `PWApp.cpp:1956–1965`, `1441–1454`.

`SaveToFile` opens the user's file with `B_ERASE_FILE` and then writes. A full
disk, a crash, a power cut between those two lines, and the document the user
had is gone — replaced by an empty or truncated file. Then `DoSave` does this:

```cpp
if (fDoc.SaveToFile(pathStr.String()) == B_OK) { ... }     // else: nothing
```

The save fails, no alert, the title still shows the document as modified, and
the user who then quits and chooses "Don't save" has lost their work with no
warning. The RTF export at `1451–1452` ignores both return values.

**Fix:** this is solved outright by Part 2 (SQLite gives you an atomic save for
nothing). Until then: write to `path + ".tmp"`, `BFile::Sync()`, rename over the
original; on any failure, `BAlert` with `strerror(err)` and leave `fModified`
set. Never `B_ERASE_FILE` the user's document.

### 4. Character formatting cannot be undone, and corrupts the undo order.

`PWDocument.cpp:441–488`.

`ApplyFormat` ends with a comment from sprint 1 promising that "format undo
arrives with the styles panel in sprint 2". It is sprint 8. `UndoStep::FORMAT`
is declared and never used. Bold, italic, underline, family, size, colour and
named styles all change the document with no undo step, so Undo after "make
this bold" undoes the *previous text edit* and leaves the bold. The user's
mental model of Undo is broken by the most common formatting action.

**Fix:** push a `FORMAT` step carrying the runs of the affected range before
the change — `Remove()` already contains exactly the code that captures a
range's runs (`362–379`); factor it out and use it here. Undo of a `FORMAT`
step re-applies the saved runs, as the `REMOVE` case already does at `602–606`.
Test: bold, undo, check `FormatAt().bold == false`.

### 5. The incremental layout reuses stale lines. Three separate ways.

`PWLayout.cpp:481–535`, `550–597`.

A paragraph is reused when its *fingerprint* matches: length, paragraph format,
first 32 bytes, last 32 bytes (`FingerprintMatch`). That is the wrong question
to ask, and it is wrong three times:

- **(a) Page setup.** `SetPageSetup()` (`14–18`) changes `fSetup` and nothing
  else. `fPrevValid` is reset only when `fDoc == NULL` (`485`). So after the
  ruler drag or Page setup ▸ Apply, `Layout()` reuses every line with its old
  `x`, `width` and wrap points. Text does not rewrap to the new margins until
  each paragraph is individually edited. The selftest "paper swap relayouts"
  (`PWApp.cpp:2410`) asserts `portraitPages >= 1` and cannot detect this.
- **(b) Character formatting.** The fingerprint does not include the runs.
  Bold a word in the middle of a paragraph: `ApplyCharFormat → Relayout →
  Layout()` → fingerprint matches → old line breaks reused, computed with
  regular-weight widths. Drawing reads the live runs, so it draws bold text on
  lines broken for regular text, and the line runs past the right margin.
- **(c) Same-length edits past byte 32.** Replace "cat" with "dog" in the
  middle of a long paragraph (`ReplaceAndFind` does Remove + Insert + one
  `Relayout`): length same, head same, tail same, format same → not
  re-measured.

**Fix:** stop guessing. The document knows what changed. Give `Para` a
`uint32 revision` bumped by every mutation that touches it (`Insert`, `Remove`,
`ApplyFormat`, `SetParaFormat`, `SplitPara`, image insert), plus a document-wide
`fLayoutEpoch` bumped by `SetPageSetup`/`SetDocument`. `PWLayout` reuses a
paragraph's lines iff `(id, revision, epoch)` match. Delete `FingerprintMatch`,
`head`, `tail`. Three tests, one per case above; each currently fails.

### 6. `PWApp::fWindow` dangles after the second window closes. Use-after-free.

`PWApp.cpp:2196–2208`, `2218`, `2085–2098`, `2106`.

File ▸ New sets `fWindow = win` (`2202`). Close that window: it deletes itself,
`'pWwc'` arrives, `CountWindows()` is still 2 (the panels, see #7, or the other
document), so the app does not quit — and `fWindow` now points at freed memory.
The next File ▸ New reads `fWindow->Frame()`; the next `hey` locks it; the next
About adds it to a subset. Any of them crashes.

**Fix:** do not cache a window in the app. When you need one, iterate
`WindowAt(i)` and `dynamic_cast<PWWindow*>`; for scripting, target the
frontmost document window. If you must cache, clear it in `'pWwc'` by passing
the closing window's pointer in the message and comparing.

### 7. After any panel is opened, the app never quits.

`PWApp.cpp:179–199`, `296–299`, `2205–2208`.

Panels hide instead of quitting (the StyledEdit pattern, fine) — but they are
`BWindow`s, hidden windows count in `CountWindows()`, and nothing ever quits
them. Open Page setup once, close the document: `CountWindows()` is 2, the
`<= 1` test fails, and ProseWriter keeps running with no window. The four
handlers `'pWpC'`, `'pWhC'`, `'pWyC'`, `'pWtq'` that null the panel pointers
are never sent by anything (grep: only the `case` lines exist) — dead code from
an earlier design.

**Fix:** in `PWWindow::QuitRequested`, post `B_QUIT_REQUESTED` to each owned
panel, or have the app count only `dynamic_cast<PWWindow*>` windows. Delete the
four dead handlers.

### 8. Images: lost on a cross-paragraph delete, leaked on every Open, phantom after Undo.

`PWDocument.cpp:413–423`, `711`, `399–407`, `152–156`.

- `Remove()` crossing a paragraph boundary merges `next` into `p` — text and
  runs, but **not `next.images`** (`413–423`). `MergeWithNext()` does move them
  (`560–562`), which shows the intent; `Remove` has its own copy of the merge
  that forgot. Delete the paragraph break before a paragraph with an image:
  the image vanishes from the document and its `BBitmap` is never deleted.
- `LoadFromMessage()` starts with `fParas.clear()` (`711`) and deletes no
  bitmaps. Every Open, every `AdoptDoc`, every `hey set Text` leaks every
  image in the previous document.
- `Remove()` deletes the bitmap of a removed image (`406`) and the `UndoStep`
  carries only text and runs. Undo re-inserts the U+FFFC marker with no image
  behind it: a phantom object character that draws nothing and measures as a
  glyph.

**Fix:** `PWImage` holds a raw pointer inside a struct that is copied by value
into `std::map`s and `std::vector<Para>` reallocations — it only works because
`Para` has no destructor. Give it value semantics: `std::shared_ptr<BBitmap>`
with a deleter. Then the leak and double-ownership questions disappear, undo
steps can carry images by copying the map, and `Remove`'s merge path can be
deleted in favour of calling `MergeWithNext()` (which is currently dead: no
caller anywhere).

### 9. Quit closes one window.

`PWApp.cpp:819`. "Quit" sends `B_QUIT_REQUESTED` to the *window*. With two
documents open, Quit closes the front one and the app stays. Target `be_app`.

### 10. Two `fprintf(stderr)` on every message the application receives.

`PWApp.cpp:2088`, `2161`. `pw-rs:` and `pw-mr:` fire for every BMessage —
every pulse, every scripting call, every drop. Leftover debugging in the hot
path. Delete both.

## Part 2 — The document format: SQLite. (The owner's decision; the design.)

**Yes, SQLite is in the distribution.** `sqlite-3.53.4.0-1-arm64.hpkg` ships in
the Prose image (CapitalBe, Filer and FairTrade require `lib:libsqlite3`), so
`libsqlite3.so.0` is on every machine. The recipe builds it with **FTS5**, FTS3,
R*Tree and column metadata; JSON functions are core since 3.38. Headers are
already built: `/Volumes/HaikuSrc/prose-packages/repo/sqlite_devel-3.53.4.0-1-arm64.hpkg`
— add it to `mksysroot.sh`, add `-lsqlite3` to `LDLIBS`, and declare
`requires: lib:libsqlite3` in the package.

**Why this fixes more than it costs.** Today's `.prose` is a flattened BMessage:
one blob, rewritten in full through `B_ERASE_FILE` (bug #3), images stored as
raw `B_RGB32` bits (a 3000×2000 photo is 24 MB in the file), no versioning, and
nothing outside ProseWriter can read a word of it. A SQLite document gives you:
atomic, crash-safe saves by construction; images stored as the original PNG/JPEG
bytes; find over an FTS5 index instead of a linear scan of `PlainText()`;
schema versioning; and a document that `hey`, the Prose portal, a script or a
future indexer can `SELECT` from. The model stays in memory exactly as it is —
this replaces `SaveToMessage`/`LoadFromMessage`, nothing else, in step 1.

### Schema, version 1

```sql
PRAGMA application_id = 0x50524F53;   -- 'PROS': lets sniffers identify the file
PRAGMA user_version   = 1;            -- the format version; see "Rules"
PRAGMA journal_mode   = DELETE;       -- NOT WAL: a document must be one file,
PRAGMA synchronous    = FULL;         --   and WAL leaves -wal/-shm beside it

CREATE TABLE document (               -- one row per key; strings, parsed by the reader
    key   TEXT PRIMARY KEY,           -- title, header, footer, default_family,
    value TEXT NOT NULL               -- default_size, page_width, page_height,
);                                    -- margin_l/r/t/b, created, modified, saved_by

CREATE TABLE paragraph (
    id     INTEGER PRIMARY KEY,       -- stable identity, never reused
    seq    INTEGER NOT NULL UNIQUE,   -- order; leave gaps (1024) so an insert
    text   TEXT    NOT NULL,          --   between two rows needs no renumbering
    format TEXT    NOT NULL DEFAULT '{}'   -- JSON: align, il, ir, fi, ls, sb, sa, list, tabs:[[x,kind]]
);

CREATE TABLE style (
    id   INTEGER PRIMARY KEY,
    name TEXT NOT NULL UNIQUE,
    chr  TEXT NOT NULL,               -- JSON character format
    para TEXT NOT NULL                -- JSON paragraph format
);

CREATE TABLE run (                    -- a styled span; NULL attribute = inherit
    paragraph INTEGER NOT NULL REFERENCES paragraph(id) ON DELETE CASCADE,
    start     INTEGER NOT NULL,       -- byte offset into paragraph.text
    length    INTEGER NOT NULL,
    style     INTEGER REFERENCES style(id),
    family TEXT, size REAL, color INTEGER,
    bold INTEGER, italic INTEGER, underline INTEGER,
    PRIMARY KEY (paragraph, start)
) WITHOUT ROWID;

CREATE TABLE image (
    id        INTEGER PRIMARY KEY,
    paragraph INTEGER NOT NULL REFERENCES paragraph(id) ON DELETE CASCADE,
    offset    INTEGER NOT NULL,       -- byte offset of the U+FFFC marker
    width_pt  REAL NOT NULL,
    height_pt REAL NOT NULL,
    mime      TEXT NOT NULL,          -- image/png, image/jpeg: the ORIGINAL bytes,
    data      BLOB NOT NULL           --   decoded by the translators on load
);

CREATE VIRTUAL TABLE paragraph_fts USING fts5(text, content='paragraph', content_rowid='id');
-- plus the three standard external-content triggers (insert/delete/update)
```

Tables in the text stay as they are — rows are paragraphs, cells split on
0x1D — because that is the model's decision, not the file's. When the model
grows a real table structure, it becomes a `cell` table; the format does not
need to know yet.

### Rules

1. **Step 1 is the drop-in.** `PWDocument::SaveToFile` becomes: open, `BEGIN`,
   `DELETE` the content tables, `INSERT` every paragraph/run/image/style,
   write `document` keys, `COMMIT`. `LoadFromFile` becomes the reverse.
   `SaveToMessage`/`LoadFromMessage` stay for the clipboard and for reading old
   files. Nothing in layout or the view changes.
2. **Step 2, when wanted, is write-through** — every edit a statement, autosave
   and a journaled undo for free. The schema is designed for it: stable `id`s,
   sparse `seq`. Do not do step 2 first.
3. **Detect the format by content, not extension.** Old files start with
   `FOB1`/`FOB2`; new ones with `SQLite format 3\0` and `application_id ==
   'PROS'`. Read both; write only SQLite. That also fixes bug #1 properly:
   sniff, don't `IFindLast`.
4. **Versioning:** `user_version` is the major format version. A reader refuses
   a newer major with a clear message. Minor changes are additive columns with
   defaults, which old readers ignore.
5. **Save As / export a copy:** `VACUUM INTO 'newpath'` — atomic, compacted,
   one statement. Never copy the file yourself.
6. **MIME:** register `application/x-vnd.prose-document` with a sniffer rule on
   the 16-byte SQLite header; keep `.prose` as the extension.
7. **Settings** (recent files at `PWApp.cpp:1153–1240`, window frame at
   `2058–2068` and `1987–1996`): two hand-parsed text files, one with a
   4096-byte cap that silently drops paths. Replace with one
   `~/config/settings/ProseWriter/settings.db` using the same library, or one
   flattened BMessage. Not text.

## Part 3 — Structure. This is why Part 1 happened.

- **`PWApp.cpp` is 2,925 lines and nine classes.** `PWWindow.h` has no
  `.cpp` (it never has — `git log` finds none); `PWApp` has no `.h`; the five
  panel classes and the find bar have no headers. Split it: `PWWindow.cpp`,
  `PWPanels.{h,cpp}` (the four `PWPanelWindow`s + About), `PWFindBar.{h,cpp}`,
  `PWScripting.{h,cpp}` (the property table, `HandleScriptingForWindow`, the
  reply helpers), `PWSelfTest.cpp`, and `PWApp.{h,cpp}` with `main`.
- **`PWWindow::MessageReceived` is 503 lines** (`1407–1911`); `SelfTest` is
  685; `BuildMenus` 150. One handler method per command; the switch dispatches.
- **Message constants.** Half are named (`OPEN_PANEL_MSG`), half are literals
  scattered across three files: `'pWnw' 'pWsV' 'pWud' 'pWrd' 'pWct' 'pWcp'
  'pWps' 'pWtI' 'pWtb' 'pWls' 'pWaq' 'pWwc' 'pWst' 'pWda' 'pWim' 'pWif' 'pWsc'
  'pWup' 'pWmg' 'pWcs' 'pprP' 'pprO'`. `'pWup'` is a literal in
  `PWPageView.cpp` *and* `DOC_MODIFIED_MSG` in the header. `'pWsv'` and
  `'pWsV'` differ by one letter's case and mean different things — that is the
  exact shape of the bug commit `61c0b24` fixed, waiting to recur. One
  `PWMessages.h`, every constant named, no literals in code.
- **Duplication:** the word-count loop (`977–982` and `1380–1387`); the
  read-a-settings-file block (`1172–1181` and `1209–1218`); insert-image-scaled-
  to-column (`1520–1532`, `1770–1789`, `1868–1879`); swap-if-reversed (`1055`,
  `1692`, `1709`, `PWPageView.cpp:674`); `AdoptDocument()` (`87–93`) and
  `PWWindow::AdoptDoc()` (`743–752`). Each is one helper.
- **`24`.** The view's page margin in pixels appears as a literal ~25 times in
  `PWPageView.cpp` and 3 in `PWRuler.cpp`, and `fPrinting ? 0 : 24` eight
  times, while `DocToView()` exists to encapsulate exactly this. The print path
  is interleaved into every drawing routine as a ternary. One `PageRenderer`
  with an origin (0 for print, the margin for screen) and a `chrome` flag; then
  `DrawPages` has one code path and `DocToView` is used everywhere or nowhere.
- **`PWLayout::fMeasureRuns`** (`PWLayout.h:176`) is a `mutable` member used as
  a hidden parameter: set, call, clear, in three places, with a comment
  referring to `fMeasurePara`, which does not exist. Pass the runs.
- **Layout is quadratic, and the benchmark hides it.** `ImageSizeAt()` calls
  `fDoc->ParaStart(para)` and `ImageAt()` → `Locate()`, both linear in the
  paragraph count, and `LayoutParagraph` calls it **per byte**, three times
  (`331`, `358`, `386`), as do `FillSegments` and `XYToOffset`. Cost is
  bytes × paragraph index. The perf test (`PWApp.cpp:2855–2861`) inserts 130
  bytes of text and then calls `SplitPara` 4,000 times — 4,000 near-empty
  paragraphs. "96 pages" is 4,000 empty 14-point lines. The "183 ms → 9 ms"
  claim was measured on a document with no text in it. Fix the algorithm
  (prefix sums for `ParaStart`, hand `LayoutParagraph` the paragraph's image
  map directly, make `ImageAt` const and drop the `const_cast` at `69`), then
  re-measure on a real corpus: 50,000 words in 500 paragraphs.
- **Per-keystroke work that undoes the incremental win.** `Relayout()` calls
  `UpdateSpellCache()`, which copies every paragraph into a `BString` and
  compares (`PWPageView.cpp:104–118`) — O(document) per keystroke. Then
  `UpdateStatusText()` rebuilds `PlainText()` (invalidated by every edit at
  `PWDocument.cpp:257`) and walks it to count words — O(document) again. The
  9 ms was the layout alone. Both should be incremental off the same revision
  counter as #5.
- **`SetCaret`** (`PWPageView.cpp:665–668`): an `if`/`else` whose two branches
  are identical. `Relayout()` calls `Window()->PostMessage` without the null
  check that `SetSpellEnabled` bothers with.
- **`PWCharFormat::Archive`** (`PWDocument.cpp:17`, `34`) type-puns `rgb_color`
  through `int32*`. Four `AddUInt8`s, or `B_RGB_32_BIT_TYPE`.
- **`LoadFromMessage`** at `730–731` replaces the *whole* run format when the
  family is empty, discarding bold/size/colour — while `PWDocument.h:27` promises
  "empty string = inherit". Fill the family only.
- **Version.** `kPWVersion = "1.0"` (`460`) and `ReplyString(message, "1.0")`
  (`1358`) are two copies; `__DATE__` as "release date" makes every build a
  release. It is not 1.0; the repo it lives in says 0.1.
- **Dead code:** `MergeWithNext()` (no callers — and its undo step at `572` uses
  an in-paragraph offset where a document offset is required); the four panel
  handlers in #7; `'pWcs'` (sent, never handled); `PWPageView(BMessage*)`
  (declared, never defined); `lastBoundary` (`PWLayout.cpp:924`); `r`
  (`980`); `isSet` (`PWApp.cpp:1278`); the empty `if` body at `PWRTF.cpp:466`.
- **`memset` on `PWCharFormat`** (`PWRTF.cpp:94`): the compiler objects, and it
  is unnecessary — `PWCharFormat prev = doc->DefaultFormat();`.
- **Makefile:** every source is compiled in one `g++` invocation, so any edit
  rebuilds 8,100 lines; the `%.o` rule is dead. Use it. Add `-Wextra
  -Wpointer-arith`; #1 was a warning.
- **RTF interop:** the writer emits each UTF-8 *byte* of a non-ASCII character
  as `\'xx` (`PWRTF.cpp:39`), which every other reader decodes as Windows-1252
  — "café" becomes "cafÃ©" in Word and LibreOffice. It round-trips only with
  itself. Emit `\uN?` from the decoded code point; read the same. And the
  reader inserts one character at a time through `PWDocument::Insert` (`234–236`,
  `273`) — a `Locate`, run surgery, `NormalizeRuns` and an undo push per
  character. Batch runs of plain characters.

## Part 4 — Tests: make 97/97 mean something.

- **`PWApp.cpp:2770–2774`** ends in `|| true`. A test that cannot fail is not a
  test; it is a number. Delete it or write the assertion.
- **The benchmark has no text in it** (see Part 3). Rebuild it on a real
  corpus and re-measure; publish those numbers instead.
- **The tests that would have caught Part 1**, none of which exist: open a
  `.prose` through `OpenFile()`; type `"\xC3\xA9"` through `KeyDown`; bold a
  word mid-paragraph and check the line width; change margins and check wrap
  points move; same-length replace mid-paragraph; New then close then New;
  open Page setup, close the document, assert the app quits; delete across a
  paragraph boundary with an image on the far side; undo a bold.
- **`tests/` is empty.** The README says it holds "guest-side test scripts and
  expected results". Fill it or correct the README.
- **Debug output in the permanent suite:** `printf("dbg ...")` at `2323`,
  `2333`, `2446`, `2553–2557`, `2708–2713`, `2756`, `2807`. Delete.
- **Weak assertions** dressed as coverage: "paper swap relayouts"
  (`portraitPages >= 1`), "landscape not taller" (`<= portraitPages + 1`),
  "incremental beats full" (`ms3 < 80` — a wall-clock threshold on a
  virtualised guest). Assert on structure, not on time.
