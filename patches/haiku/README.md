# Haiku fork patches

These apply on top of Haiku **hrev60122**. We maintain our own fork; see `haiku_virtualized.md` §1.5 for why none of this goes upstream.

| Patch | What it does | Why |
|---|---|---|
| 0001 | The arm64 kernel keeps a RAM copy of all its debug output, starting with the tag `HAIKU-RAMLOG-V1` | Apple's Virtualization.framework gives the guest no UART. `tools/hvgpu`'s RAM console reads this buffer from guest memory, including panics and KDL output |
| 0002 | `virtio_gpu` refuses GPUs that don't offer `VIRTIO_GPU_F_EDID` | Under VZ, app_server would otherwise open VZ's own virtio-gpu first and hang. Our custom GPU offers EDID |
| 0003 | `virtio_pci`, modern-interface fixes: (a) the driver's accepted features are written to `driver_feature(_select)`, not the read-only `device_feature(_select)`; (b) transitional devices (IDs 0x1000–0x103f) that expose the modern capabilities use the modern interface; (c) capabilities are read by `cap_len`, not `length`; (d) notify offsets start as "unset" and notifies are range- and magic-checked; (e) 64-bit queue addresses are written as two 32-bit halves; (f) interrupts that find ISR 0 are counted | (a) Haiku never told a modern device which features it accepted. QEMU shrugs; VZ's block and GPU devices refuse to operate without `VERSION_1`, which is why virtio-blk failed under VZ. (b) The legacy interface uses I/O ports, and on arm64 the PCI layer reports host address 0 for every I/O BAR (`pci_ram_address()` only knows memory ranges), so all legacy devices aliased whichever sat at I/O address 0: initializing virtio-net reset the disk. That was QEMU's `pci-blk`/`pci-scsi` failure. (c) VZ's notify regions are tiny, so `notify_off_multiplier` was never read and `virtio_net` notified random kernel addresses. (d)–(f) are defences and diagnostics, plus the spec's §4.1.3.1 access rule |
| 0004 | The EFI loader numbers CPUs in MADT order, with the CPU it runs on as 0 | VZ's MADT reports GICC "CPU interface number" 0 for every CPU, which is valid for GICv3. Using it as the id made every CPU look like the boot CPU, so none were started and the kernel waited for them forever |
| 0005 | The loader's PSCI calls follow SMCCC: x0–x3 are in/out, x4–x17 are clobbered, and the status is returned | The asm declared inputs only, which is wrong for any PSCI implementation that writes more than x0. It also logs each `CPU_ON` result |
| 0006 | The loader logs "Entering the kernel on the boot CPU" | Shows in the RAM console where the loader hands over |
| 0007 | `virtio_block` logs every request that fails or times out (op, sector, length, vectors, wait result, elapsed, status byte) | Distinguishes "device never answered" (timeout, status 255) from "device rejected" (status 1/2) without a debugger |
| 0008 | The virtio bus manager logs the device's offered and the driver's accepted feature bits, in hex, for every device | The negotiation is where both VZ failures hid |
| 0009 | Shutdown and reboot through PSCI `SYSTEM_OFF`/`SYSTEM_RESET`; the loader passes the conduit (HVC/SMC) in `kernel_args` | `arch_cpu_shutdown()` was a stub, so "Shut down" did nothing and VMs could only be force-stopped |
| 0010 | The loader reads UEFI `GetTime()` before `ExitBootServices` and the kernel's RTC counts on from it | There is no RTC on arm64 Haiku, and none at all under VZ; the clock started at 1970 |
| 0011 | `acpi_gpio_events`: ACPI GPIO-signalled events on a PL061 (`ARMH0061`, `_AEI` → `_Exx`/`_Lxx`); `acpi_button` enabled for arm64; the private `acpi.h` gains the GPIO resource | This is how VZ signals the power button. Only the registers Linux's pl061 driver touches are written, and only the event pins' bits: VZ's PL061 model terminates the VM on unexpected writes (`AFSEL`, or `IC` bits of unconfigured pins) |
| 0012 | Per-interrupt trigger configuration for GICv3 (`GICD_ICFGR`), and `arch_int_configure_io_interrupt()` on arm64 | All SPIs were level-sensitive; edge sources that pulse their line, like QEMU's GED, were lost |
| 0013 | `acpi_gpio_events` also handles the ACPI Generic Event Device (`ACPI0013`, `_EVT(irq)`) | QEMU's `virt` signals the power button this way; `system_powerdown` now ends in a clean PSCI `SYSTEM_OFF` |
| 0014 | Virtio shared memory (`VIRTIO_PCI_CAP_SHARED_MEMORY_CFG`) in `virtio_pci` and the bus manager (`get_shared_memory()`), plus the `prose_display` kernel driver for the S2 device (`docs/s2-display-device.md`): maps the surface pool, sets the mode, posts event buffers, publishes `graphics/prose_display/0`; milestone A draws a test pattern from a kernel thread | The zero-copy display. Region 0 shows up as a 64-bit BAR (BAR 4 at 0x180000000 on VZ), so this also exercises the 64-bit BAR path |
| 0015 | `prose_display.accelerant` (app_server draws into the cloned surface pool), the optional accelerant hook `B_COMMIT_RECTANGLES` in `Accelerant.h`, `AccelerantHWInterface` calling it after `_CopyBackToFront()` and `_DrawCursor()`, and the driver ioctls behind it (`CLONE_POOL`, `SET_MODE`, `COMMIT`; retrace semaphore owned by the opener) | The desktop on the zero-copy display, paced by the host's vsync. User space may not acquire kernel-owned semaphores, hence the ownership hand-over at `open()` |
| 0016 | Live resize: `PRDS_WAIT_MODE_HINT` ioctl (the wait happens inside the driver, so the semaphore stays kernel-owned), `prose_display_agent` server (launched from `data/launch/system`, follows the host window with `BScreen::SetMode()`), `REDRAW` → full commit; the retrace semaphore is only handed to the first opener | The guest desktop follows the host window, like guest tools on other hypervisors |
| 0017 | Tear-free commits: the accelerant's `B_COMMIT_RECTANGLES` hook sends `PRDS_COMMIT` synchronously and returns when the host has copied the rects (the vsync-paced commit thread is gone); `_DrawCursor()` commits only the cursor's frame; a pool bandwidth check at accelerant init | app_server may not overwrite a rect the host is still reading; the 16 ms window of the asynchronous commit was where tearing came from |
| 0018 | app_server's back buffer in the surface pool: optional accelerant hook `B_GET_BACK_BUFFER_CONFIG` in `Accelerant.h`, app_server's `DeviceBackBuffer` replacing `MallocBuffer` when the hook answers, the driver reserving the region after the largest front buffer | Both buffers app_server works with become reachable by the host's GPU — the prerequisite for a bb → display blit kernel |
| 0019 | `virtio_input`: a device whose configuration carries the `PRIN1` marker is queried from a static table after the standard configuration instead of with select/subsel writes | Apple's Virtualization.framework never delivers configuration writes to custom virtio devices; this is how hvgpu's own keyboard and tablet describe themselves. QEMU's devices still use the standard protocol |
| 0020 | `prose_display_agent` switches once the host window has stopped moving (250 ms quiet, 1.5 s cap); `PRDS_WAIT_MODE_HINT` returns at once when the host's size differs from the caller's last applied size | A drag no longer causes a mode switch every 170 ms trailing the corner, and no hint can be lost |
| 0021 | `virtio_net`: header size follows `VIRTIO_F_VERSION_1` (12 bytes on modern devices), the driver asks for `VIRTIO_NET_F_CSUM` and checks the negotiation result, MTU stored as a frame size; the bus manager logs a refused `FEATURES_OK` and retries with everything offered, then the bare transport | Networking never worked under VZ (misframed packets; Apple's virtio-net refuses any feature set without CSUM). Also latent on QEMU since patch 0003 drives transitional devices as modern |
| 0022 | `virtio_sound`: a real hmulti_audio driver (stereo S16 48 kHz playback, buffers paced on a steady schedule anchored to the device's completions); device manager publishes `/dev/<class>` directories after boot (upstream TODO); `virtio_pci` interrupts request a reschedule; media stack + `prose_tone` in the image | Sound through VZ's and QEMU's virtio-snd. Without the device-manager fix `/dev/audio` never existed; without the pacing the node dropped buffers on hosts that complete in bursts |
| 0023 | `prose_midi`: the Prose MIDI virtio device (ID 62) as `/dev/midi/prose/0`, a raw MIDI byte stream `midi_server` turns into a port; `prose_midi_test`; device manager: `midi` path tables, no directory for a module's own name | The guest's MIDI played by the Mac's General MIDI synth and exposed to CoreMIDI. | 0024 | HostFS: `virtio_fs` (boot module) moves FUSE requests for virtio-fs devices and publishes each as a read-only pseudo-disk `/dev/disk/virtual/virtio_fs/<n>/raw` naming the device's tag; the `hostfs` file system (FUSE 7.31 client) recognises it and mounts it; node table with FORGET, file cache with close-to-open consistency; mount_server always mounts HostFS volumes | A folder on the Mac as a disk in Haiku (`hvgpu --share DIR`): mounted at boot at `/<tag>` (default `/HostFS`), on the Desktop and in Tracker's Mount menu. VZ's own virtio-fs device and FUSE server do the host side |
| 0025 | HostFS: Haiku attributes as host xattrs `user.haiku.<name>` (type code + data, the build tools' convention), `BEOS:TYPE` emulated from the extension when none is stored; directories read with `FUSE_READDIRPLUS` so `d_ino` is the vnode ID; idle nodes (≤ 2048) kept instead of forgotten at once | Tracker needs attributes for icons and types and starts node monitoring from `d_ino`; applications copied to the Mac keep their icons and signatures |
| 0026 | HostFS: attribute reads in one round trip (4 KiB first, size query only on `ERANGE`); `create_attr` without `O_TRUNC` keeps the data on a type change; `hostfs` also linked from `kernel/boot` | Tracker reads several attributes per file; the loader preloads every file system, and the preloaded image now keeps a valid path after boot |
| 0027 | HostFS review fixes: stale files are only marked from lookups/readdir and refreshed from hooks that hold the vnode (no panic when a mapped program changes on the Mac; its old pages stay until it exits); per-node size lock (write-back shared, size changes exclusive) and refresh gate, so concurrent appends and truncation cannot lose or resurrect data; close re-stamps only for the last writer; case-only renames reach the host; `virtio_fs` polls a queue whose completion is late and copies non-kernel addresses with `user_memcpy` | Found by an independent review and reproduced by `private_workspace/hostfs-hard.sh` (one lost append in 800 before the fix) |
| 0028 | `virtio_input`: Control+Command+Delete opens the Team Monitor, checked on the key state like the keyboard add-on (Delete down while the keymap's left Command and Control keys are down); the key events that follow go to the window until the first key-up, which stops the forced-reboot count and leaves the window open. `TeamMonitorWindow.cpp`/`TeamListItem.cpp` are built from the keyboard add-on's directory, and its `Keyboard.rdef` signature finds the Team Monitor's translations | The Team Monitor was only in the keyboard (PS/2, USB) add-on, so under VZ, whose keyboard is hvgpu's virtio-input device, ⌃⌘⌦ and Machine ▸ Send Keys ▸ Control-Alt-Delete did nothing |

To add a change: commit it on `prose`, then

```sh
/Volumes/xb/HaikuArmQemu/scripts/export-patch.sh     # writes the next NNNN-<subject>.patch
```

It first puts the record into the commit (`Prose-Patch: <file> <hash>`, the
hash being of the diff alone, `scripts/patch-diff-hash.sh`, which is the same
for the commit and the file); then add the row above. A patch whose diff was
edited after it was applied makes `apply-patches.sh` stop and say so (the hash
no longer matches the record); run `export-patch.sh` again on the amended
commit, or rebuild `prose` from the patches (`git branch -D prose`, build).
